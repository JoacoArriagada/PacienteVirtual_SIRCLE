# Qué queremos probar con LR

Documento de conversación para la revisión con el profesor. Las alternativas siguen abiertas. La referencia visual es el HTML de Semana 5. La fuente clínica es el escenario original de LR en MedSP1000.

## La pregunta que ordena el resto

Cuando el profesor dice «una iteración», podría querer observar dos cosas distintas. Una es que un estudiante pueda hablar con una paciente virtual en su propio computador. Otra es que esa conversación le sirva para decidir qué medir y justificar una hipótesis. Las dos caben en el proyecto, pero se evalúan de forma diferente. Para la primera bastaría una entrevista breve que admita preguntas nuevas. Para la segunda habría que observar qué hace el estudiante después de escuchar a LR. ¿Cuál te pidió el profesor y cuál quieres defender tú como aporte de la práctica?

## Qué papel tendría Qwen

**Entender y redactar son dos tareas diferentes.** Qwen podría reconocer que «¿desde cuándo empezó?» y «¿hace cuántos días le pasa?» solicitan el mismo antecedente, y recuperar una respuesta del guion. Ese diseño facilita comprobar cada dato. También podría redactar la respuesta en el momento a partir de hechos autorizados. Eso permitiría variar la conversación y dar más naturalidad a los turnos de seguimiento, con mayor exigencia de revisión. ¿Qué parte haría que tú y el profesor sintieran que realmente están conversando con LR?

**El guion ofrece una prueba especialmente buena.** Según el original, LR conoce el inicio de sus síntomas y desconoce sus antecedentes familiares porque fue adoptada. Una entrevista creíble debería distinguir ambos tipos de conocimiento, aceptar una paráfrasis y sostener el contexto cuando el estudiante repregunta. También puede haber una respuesta clínicamente compatible con el caso que conteste otra cosa. Conviene pedirle al profesor algunas preguntas que no hayamos utilizado al preparar el guion. [Guion original del actor](<../../../datos/medsp1000/mededportal_10181/scenario1/sp_actor/Case A-Asthma.md>)

**4B responde a una restricción concreta.** Querer ejecutarlo en el computador del profesor es una buena razón para considerar esa escala. El dato decisivo será qué tan fluida se siente una entrevista en ese equipo, con el historial de varios turnos y también en la primera consulta tras abrir el modelo. ¿Esperas que el profesor lo pruebe solo o que varios estudiantes utilicen el mismo equipo servidor? Son dos escenarios de viabilidad distintos.

## Las decisiones técnicas que planteaste

| Propuesta | Qué justificaría elegirla |
|---|---|
| **HTML, TypeScript y React** | Ya existe una interfaz navegable con un comportamiento que quieres preservar. TypeScript puede servir para definir con precisión qué datos intercambian el caso, una medición y el chat. React es una decisión independiente sobre cómo construir la interfaz. Dado que prefieres evitarlo, ¿hay algún problema concreto del HTML actual que exija cambiar de framework? Si lo que falta es la entrevista, esa pregunta puede estudiarse conservando las pantallas. |
| **Rust o Spring Boot para el backend** | Rust con Axum encaja si también quieres aprender Rust y podrás mantenerlo. Spring Boot es un framework de backend del ecosistema Java y puede encajar si quienes continuarán el proyecto ya lo conocen. Ambos podrían conectar la interfaz con un motor local. ¿Quién tendrá que entender o modificar el proyecto después de tu práctica? |
| **Monorrepositorio y responsabilidad única** | Tener el frontend y el backend en un repositorio facilita entregar una versión coherente al profesor. Más adelante se podrían reconocer tres responsabilidades por dónde cambia cada cosa: una pantalla, una regla de LR o la conexión a Qwen. Un controlador recibe la petición, un DTO describe los datos que cruzan la frontera y una interfaz resulta útil cuando hay implementaciones intercambiables. Un constructor prepara un objeto. ¿Qué cambio quieres poder hacer tocando un solo lugar? Eso orienta mejor las carpetas que fijar ahora una cantidad de módulos. |
| **Base de datos, MongoDB o una solución local** | Primero hay que definir qué significa «retomar». Si basta volver a la pestaña durante la clase, el navegador ya cubre parte de la necesidad. Si la conversación y la hipótesis deben sobrevivir al cierre y estar disponibles para el profesor, un archivo SQLite por instalación es una opción. MongoDB tendría más sentido si existe un motivo para mantener una base documental como servicio. ¿Qué debe seguir disponible mañana, para quién y desde qué equipo? |
| **Docker Compose y volúmenes** | Un comando de arranque es valioso cuando el profesor necesita una entrega reproducible. Llevar también Ollama a un contenedor puede exigir preparar otra copia del modelo y verificar el acceso a la GPU. Reutilizar el Ollama del equipo reduce ese trabajo para una primera prueba. Los pesos del modelo y el avance de una práctica son datos con ciclos distintos. ¿Tu prioridad es que funcione en el computador concreto del profesor o distribuir el mismo entorno a varias estaciones? |
| **Diagrama de funcionamiento** | Un diagrama de despliegue responde qué arranca, dónde corre Qwen y dónde se guarda el intento. Un flujo de atención responde qué ocurre desde que el estudiante pregunta hasta que una respuesta se vuelve evidencia. ¿Qué necesita entender el profesor en esta reunión? Se puede presentar primero el flujo docente y dejar el despliegue como hipótesis técnica. |
| **Figma y recursos ordenados** | Tiene sentido conservar paleta, Roboto, iconos, escenas y expresiones en un lugar común. El Figma fija la intención visual, el HTML muestra el comportamiento previo y MedSP1000 aporta el caso. Que la pantalla de presión se vea igual y que muestre el valor aprobado son dos comprobaciones distintas. ¿Qué aspectos visuales considera el profesor indispensables para reconocer SIRCLE? |
| **Los 16 casos de uso y Spec Kit** | Los 16 casos orientan el proyecto completo. Para esta discusión importan sobre todo iniciar o retomar, valorar, registrar decisiones, conservar avance y solicitar exámenes. Una vez acordada la experiencia, Spec Kit podría convertir un recorrido concreto en criterios de aceptación y tareas. ¿Qué tendría que quedar acordado con el profesor para que esa especificación represente sus expectativas? |

## Orden sugerido antes de construir

1. **Elegir la pregunta docente.** Acordar qué tendría que poder hacer o explicar el estudiante al terminar.
2. **Delimitar LR.** Escoger la fase del caso, qué información está disponible al inicio, qué sabe la paciente y qué se descubre mediante acciones.
3. **Recorrer el HTML con el profesor.** Anotar qué conserva, qué cambia y en qué momento entra la IA. Bastan una pregunta libre, una medición y una decisión para discutir el recorrido.
4. **Acordar cómo juzgar la conversación.** Preparar ejemplos de respuesta correcta, incertidumbre legítima, pregunta ambigua y dato inventado. Reservar preguntas nuevas para la revisión.
5. **Elegir arquitectura y especificación según las respuestas.** El equipo objetivo, la necesidad de retomar y quién mantendrá el proyecto permiten decidir con fundamento sobre framework, persistencia y despliegue.

Para empezar la conversación bastaría elegir qué observar primero: si el estudiante logra entrevistar a LR con naturalidad o si logra tomar una decisión mejor fundamentada a partir de la entrevista.
